# Context management problem （上下文管理问题）导致的 token bloat（token 膨胀）与 context clash（上下文冲突）以及 智能体轮次和工具并发控制问题导致的研究过度扇出（fan-out）

## 成本感知的上下文治理与研究扇出控制

**改动名称：成本感知的上下文治理与研究扇出控制（Cost-aware Context Governance and Research Fan-out Control）。**

本项目建立在 LangGraph 的 Supervisor–Researcher 多智能体架构之上，完整流程包括用户澄清、研究简报生成、Supervisor 任务规划、Researcher 工具检索、研究结果压缩以及最终报告生成。系统的优势是能够根据中间结果动态调整研究路径，并通过多个独立上下文并行探索复杂问题；但这种能力也带来了**显著的工程代价**：研究单元、工具调用、搜索查询、网页结果和摘要任务会逐层展开，使少量上层决策被放大为大量模型调用与上下文输入。

本次改动的直接原因，是项目评测中已经出现**明显的 token bloat、工具反馈膨胀、上下文累积和研究过度扇出**。高难任务曾消耗数十万乃至百万级 token，但更高的资源投入并未稳定转化为更高真实性，反而伴随重复搜索、低质量来源混入、引用错配和任务范围扩张。这说明 DeepResearch 的主要矛盾并不是“研究得不够多”，而是缺少**对研究资源的有效分配与收敛机制**。

这项改动的核心启发是：**系统的能力上限不应等同于默认执行强度。** 一个优秀的研究智能体并非始终启动最多的子智能体、执行最多的搜索，而应根据任务复杂度、信息缺口和证据价值决定投入多少资源。换言之，DeepResearch 应从“能力驱动的无限探索”转向“**预算约束下的自适应研究**”。

其核心思想可概括为三层治理。第一层是**配置治理**：通过 `max_concurrent_research_units`、`max_researcher_iterations`、`max_react_tool_calls`、`max_concurrent_researcher_tool_calls`、`max_queries_per_search_call` 和 `max_results_per_tavily`，分别约束 Supervisor **广度**、研究迭代**深度**、Researcher 工具轮次、单轮工具**并发**以及 Tavily 内部搜索规模，使原本隐性的成本边界成为**显式可配置**的系统接口。

第二层是**运行时治理**：Supervisor 只执行配置允许数量的 `ConductResearch` 调用，Researcher 只并发执行限定数量的工具；超出预算的调用不会被静默丢弃，而是返回对应的错误型 `ToolMessage`，从而在限制并发的同时保持工具调用协议完整。Tavily 搜索进一步限制单次 query 数、每个 query 的返回结果数，并使用 semaphore 控制单次搜索内部的网页摘要并发。

第三层是**行为与上下文治理**：Supervisor 提示词强调优先使用**单个** agent、能够回答时立即停止；Researcher 遵循“**先广后窄**”的检索策略，在建立问题全貌后只对高价值缺口继续深入，并在结果重复或证据已经充分时**终止搜索**。网页摘要阶段则通过正文长度限制、**结构化** `summary` 与 `key_excerpts` 输出，将原始网页转换为更适合下游推理的**压缩**信息。

本次改动还加入了轻量级 **Process Trace**，为 research brief、Supervisor、Researcher、搜索、网页摘要、压缩和最终报告节点分配层级化编号，并记录轮次、工具名称与并发关系。它不直接减少 token，却使隐藏的**并发扩张变得可观察**，为后续统计 `tokens_per_claim`、`tool_calls_per_claim` 和 `marginal_gain_per_round` 提供了必要的观测基础。

这套机制的价值不只是降低费用。它能够缩短响应时间、减少重复来源、缓解上下文冲突，并促使模型把有限预算优先用于高价值证据。项目测试已经验证了并发截断、Tavily query 限制、摘要并发控制、结构化摘录兼容和运行追踪等行为，说明这些约束已经从提示词建议转化为可测试的工程规则。

从更长远的意义看，本次改动完成的是 DeepResearch 工程范式的转变：系统不再只追求“能够查多少”，而开始关注“每一次调用产生了多少有效信息”。它为后续引入任务难度识别、全局 token 预算、动态模型调度、证据卡片和边际信息增益终止机制建立了基础。

**一句话总结：本次改动通过对研究广度、深度、并发和上下文规模进行显式配置，使 DeepResearch 从容易失控的开放式搜索系统，转变为可观察、可约束、可评估且更加经济可靠的工程化研究系统。**


## 面向多智能体 DeepResearch 的上下文治理与提示词工程优化

### 一、工作定位：从“让智能体多搜索”转向“让系统有边界地研究”

该项目采用典型的 Supervisor–Researcher 分层架构：

* 研究简报负责将用户对话压缩为明确的研究目标；
* 监督智能体负责理解全局任务、拆分子任务、调度研究智能体并判断是否结束；
* 研究智能体负责执行搜索、评估证据和补齐信息缺口；
* 压缩模块将各研究智能体的结果整理后交给最终报告生成器。

在代码中，用户消息首先被转换为 `research_brief`，监督智能体主要接收该简报而不是完整原始研究上下文；监督智能体再通过 `ConductResearch` 创建相互隔离的研究子任务。 这本质上属于一种 **Orchestrator–Worker（编排者—工作者）模式**：由中央监督者维护全局目标，由子智能体在独立上下文中完成局部研究。Anthropic 的多智能体研究系统和 OpenAI 所描述的 Manager Pattern 都采用了类似思想。

你的优化目标可以概括为：

> **在保证复杂研究任务具有充分探索能力的同时，限制无价值的上下文增长、研究扇出和重复搜索，使研究过程最终能够基于证据充分性而收敛。**

这已经从传统 Prompt Engineering 上升到了 Context Engineering。上下文工程关注的不只是“提示词怎样写”，而是如何在有限上下文中选择、组织、传递和压缩最有价值的信息。

### 二、上下文管理：控制信息在系统中的产生、流动和终止

#### 1. 通过任务分层实现上下文隔离

监督智能体不亲自完成所有搜索，而是将任务拆分为独立的 `research_topic`。每个研究智能体只能看到自己的子任务，这避免了所有智能体共享全部历史、全部搜索结果和全部工具输出。

这种设计实现了三种隔离：

| 隔离类型  | 作用                    |
| ----- | --------------------- |
| 目标隔离  | 每个研究智能体只解决一个明确子问题     |
| 上下文隔离 | 子智能体不需要读取其他智能体的完整消息历史 |
| 工具隔离  | 每个子智能体独立执行自己的搜索循环     |

LangChain 将多智能体系统的核心价值之一直接归纳为 Context Management：让每个智能体只获得完成当前任务所需的上下文，而不是将全部信息塞入同一个上下文窗口。

你在提示词中进一步要求每个 `ConductResearch` 指令包含研究目标、任务边界、关键问题、来源类型和预期输出，实质上是在优化 **Subagent Input Context**：既保证子智能体拥有足够信息，又避免把无关全局背景传递进去。

#### 2. 通过并行门控防止研究过度扇出

原始多智能体系统容易产生一个典型问题：

> 只要任务能够拆分，就同时创建大量子智能体。

但“可以拆分”不等于“值得并行”。并行会同时增加：

* 模型调用次数；
* 搜索工具调用次数；
* 网页摘要任务；
* 子智能体结果长度；
* 监督智能体后续合并负担。

你将并行条件收紧为：

> 只有当研究方向明确、相互独立、不重叠，并且并行确实能够提升覆盖率或效率时，才使用多个研究智能体。

这是一种 **Parallelization Gating（并行门控）**。它把“是否拆分”从结构判断变成了成本—收益判断，也与现代智能体工程中“优先增强单智能体，必要时再使用多智能体”的原则一致。

项目代码同时提供了确定性保护：超过 `max_concurrent_research_units` 的委派不会执行，允许的研究任务则通过 `asyncio.gather` 并行运行。 因此系统形成了两层约束：

* 提示词负责让模型主动节省预算；
* 代码负责在模型违反约束时强制截断。

这属于 **Soft Policy + Hard Guardrail（软策略与硬护栏结合）**。

#### 3. 根据任务复杂度动态分配研究预算

你没有让所有任务统一执行相同深度，而是区分：

* 简单事实问题：直接定位关键事实，使用 1–2 次搜索；
* 复杂问题：通常不超过 3 次，存在关键缺口或证据冲突时最多增加到 5 次；
* 开放式研究：先建立问题地图，再逐步深入重点方向。

这属于 **Complexity-Aware Budgeting（复杂度感知预算分配）**。它解决的是资源错配问题：

* 简单任务不应为“看起来像 DeepResearch”而执行完整探索流程；
* 复杂任务又不能因为固定的低预算而过早停止；
* 额外预算必须由信息缺口、来源冲突或关键维度缺失触发。

需要准确说明的是：这些规则目前控制的是搜索工作量，而不是直接控制 Token。代码实际统一使用 `max_react_tool_calls` 限制研究智能体循环轮数，同时分别限制并行工具数、每次搜索的查询数以及每个查询的结果数。

因此，你实现的是 **Token 的间接治理**：

> 通过减少智能体数量、搜索轮数、并行工具数、查询数和网页数量，降低后续进入上下文的 Token 总量。

#### 4. 从固定来源数量转向证据充分性停止

你删除了“得到三个来源就停止”这一机械条件，改为根据以下因素判断是否完成：

* 用户要求的关键维度是否覆盖；
* 核心结论是否获得权威、直接且相关的证据；
* 剩余缺口是否会实质性影响答案；
* 最近搜索是否产生了新的关键事实或更高质量来源；
* 下一轮研究的预期信息增益是否高于成本。

这是一种 **Evidence-Sufficiency Termination（证据充分性终止）**，也是本次修改中最重要的部分。

固定来源数量无法代表研究完成度：

* 一个发布日期问题可能只需要一个官方页面；
* 一个多模型横向比较即使获得三个来源，也可能没有覆盖全部比较对象；
* 十个相互转载的二手来源，证据价值可能低于一个官方原始文档。

你的停止逻辑因此从：

> 搜索了多少？

转变为：

> 用户需要的结论是否已经能够被可靠地回答？

进一步加入“预期信息增益相对于成本较低”后，系统开始具备近似的 **Marginal Utility（边际效用）判断**：当新增搜索不再产生实质信息时主动收敛，而不是消耗全部可用预算。

### 三、提示词工程：将自然语言要求转化为智能体执行协议

#### 1. 将角色描述改造成可执行决策流程

你的提示词不再只告诉监督智能体“负责管理研究”，而是明确规定了完整决策流程：

1. 识别关键问题、维度、约束和证据要求；
2. 判断是否需要委派；
3. 判断是否需要并行；
4. 为每个子任务定义目标和边界；
5. 检查返回结果的覆盖度和证据质量；
6. 决定继续研究还是调用 `ResearchComplete`。

这属于 **Procedural Prompting（过程化提示）**：将抽象职责拆成一组可观察、可执行的步骤。OpenAI 的智能体工程指南同样强调，复杂指令应拆成清晰步骤，并让每个步骤对应明确动作或输出，以减少解释歧义。

#### 2. 为工具建立明确的调用语义

你为三个工具划分了不同职责：

* `ConductResearch`：获取新的外部信息；
* `think_tool`：分析现有信息并决定下一步；
* `ResearchComplete`：显式终止研究循环。

这实际上定义了一个研究智能体状态机：

> 规划 → 执行 → 评估 → 继续或终止

其中 `ResearchComplete` 是显式终止信号，避免模型只能通过“不再调用工具”隐式结束。项目代码会在检测到该工具、没有工具调用或达到循环上限时退出监督流程。

#### 3. 将反思从自由思考改造成质量检查

你没有让 `think_tool` 进行宽泛的自由推理，而是规定它检查：

* 已获得什么证据；
* 来源是否权威；
* 哪些要求仍未覆盖；
* 是否存在冲突；
* 下一轮搜索能否产生实质收益。

因此，`think_tool` 在系统中承担的不是知识获取，而是：

> Coverage Check + Evidence Check + Gap Analysis + Continue/Stop Decision

也就是覆盖检查、证据检查、缺口分析和继续/停止决策。

这种设计适合长工具链、序贯决策和需要分析工具返回结果的任务。Anthropic 的实验也表明，`think` 工具主要适合复杂工具链、工具结果分析和逐步决策，而不适合简单或非序贯工具调用。

不过，你当前要求“每次调用 ConductResearch 前都必须使用 think_tool”，属于偏保守设计。在当前代码中，每次监督模型调用都会增加 `research_iterations`，因此额外反思会消耗监督循环预算。

这意味着该设计本质上是在做取舍：

> 用更多规划成本换取更低的错误委派率和研究扇出风险。

对于复杂研究合理；对于简单任务，未来可进一步考虑只在首次委派、追加委派和结束前强制反思。

#### 4. 建立来源层级和证据使用边界

你没有简单规定“只能使用官方来源”，而是建立了来源分层：

| 来源层级                   | 主要用途             |
| ---------------------- | ---------------- |
| 官方文档、原始论文、政府与标准资料、官方仓库 | 支撑核心事实和核心结论      |
| 专业媒体、二手文章              | 补充背景或发现线索        |
| 社区讨论、用户评价              | 了解实际体验、问题和争议     |
| 聚合来源                   | 辅助定位原始信息，不作为核心证据 |

这种设计同时避免了两个极端：

* 完全不限制来源，导致二手文章和聚合页面支撑关键结论；
* 完全禁止非官方来源，导致无法研究用户体验、行业争议或实际部署问题。

其核心原则是：

> 非权威来源可以扩展研究视野，但不能独立建立关键事实。

这属于 **Source-Aware Prompting（来源感知提示）** 和 **Evidence Hierarchy（证据层级设计）**。

### 四、你实际构建的是一套“上下文漏斗”

从整个项目看，信息不是被原样不断追加，而是经过多级筛选和压缩：

```text
用户对话
   ↓ 任务理解与范围收敛
Research Brief
   ↓ 子任务拆解与上下文路由
Research Topic
   ↓ 搜索、去重与网页摘要
Search Evidence
   ↓ 子智能体研究压缩
Compressed Research
   ↓ 监督智能体筛选与合并
Research Notes
   ↓ 最终综合
Final Report
```

Tavily 搜索会限制查询数和结果数、按 URL 去重，并对网页正文进行摘要。 每个研究智能体结束后，又通过 `compress_research` 将工具输出压缩为 `compressed_research`，再返回监督智能体。 最终报告生成器只基于聚合后的研究笔记和研究简报生成答案。

因此，你的工作覆盖了上下文生命周期中的前半部分：

* 控制任务范围；
* 控制上下文分发；
* 控制信息生产速度；
* 控制并行扩散；
* 控制搜索深度；
* 控制研究终止；
* 控制进入上下文的证据质量。

它可以被正式概括为：

> 一套面向多智能体 DeepResearch 的成本感知上下文治理与证据驱动研究调度方案。

### 五、这套工作的工程价值与当前边界

你的设计主要解决了四类失控问题：

| 失控问题              | 对应机制                     |
| ----------------- | ------------------------ |
| Token bloat       | 简单/复杂任务分流、查询预算、来源去重、停止条件 |
| Research fan-out  | 单智能体优先、独立性判断、并发上限        |
| Over-exploration  | 由广到窄、信息增益判断、最大搜索预算       |
| Evidence dilution | 来源分层、权威证据优先、非权威来源核验      |

但它目前仍以提示词层面的启发式治理为主。代码已经硬性限制并发、查询数、结果数和循环数，但以下规则尚未完全结构化：

* 简单任务与复杂任务的自动分类；
* 实际累计搜索次数；
* 每轮新增信息增益；
* 每个有效结论消耗的 Token 和工具调用；
* 来源权威等级；
* 关键维度覆盖率。

此外，当前压缩提示词仍要求尽可能保留全部相关信息和全部来源，并允许输出“尽可能长”，这可能抵消前面搜索治理带来的部分 Token 节省。

因此，从成熟度上看，你已经完成了：

> 从无边界的 Agentic Search，升级为具有任务分级、资源预算、并行门控、证据质量控制和停止协议的 Budgeted DeepResearch。

下一阶段则应将提示词中的软规则逐步变成可观测、可计算和可执行的运行时指标，使系统从“模型自行判断是否节省”进一步演进为“模型判断与程序控制共同决定研究预算”。



## 分析


当前项目的 token 消耗问题，本质上不是简单的“最终报告生成过长”，而是 DeepResearch 架构在执行开放式研究任务时产生的 **token bloat（token 膨胀）** 、**context accumulation（上下文累积）**、**tool-feedback expansion（工具过度反馈）** 和 **multi-agent coordination overhead（多智能体协调开销）** 的叠加结果。


其一，deep research天然执行开放式研究任务天然高成本
  

    Anthropic 在其多智能体研究系统复盘中给出了经验：multi-agent research 的优势在于通过多个独立上下文窗口并行探索复杂问题，但代价是 token 消耗显著上升；其内部数据表明，普通 agent 通常约为聊天交互的 4 倍 token，而 multi-agent 系统约为聊天交互的15 倍 token。

    Anthropic 还特别强调，multi-agent 架构主要适用于高价值、可并行、信息量超出单一上下文窗口的任务；而许多 coding 类任务并没有足够多真正可并行的子问题，因此并不总是适合默认启用多智能体扩展。 

**并发控制**，观察到最消耗token的地方往往是异步并发处，需要对齐进行控制，主要是三个并发位置：

| 位置                               | 主流程 | 并发对象                                    | 触发条件                                       |
| -------------------------------------- | ------: | --------------------------------------- | ------------------------------------------ |
| **Supervisor 同时启动多个 researcher**       |       是 | 多个子研究任务并发                               | Supervisor 一次调用多个 `ConductResearch`        |
| **Researcher 同一轮并发执行多个 tool call**     |       是 | Tavily / MCP / search / think 之外的工具调用并发 | Researcher 模型一次返回多个工具调用                    |
| **Tavily 多 query 并发搜索 + 多网页并发摘要**      |       是 | 多个搜索 query、多个网页 summarization 并发        | Tavily 工具收到 `queries: List[str]`           |


第二，supervisor-subagent 架构存在 fan-out effect（扇出效应）。

    Open Deep Research 的 supervisor 会判断 research brief 是否可以拆成多个独立子主题，并委派给不同 sub-agents；这种设计可以隔离上下文并提升并行搜索能力，但一旦任务本身不需要并行，子任务数量、工具调用轮数和网页内容长度会共同放大成本。

第三，工具反馈是主要 token 来源

    Open Deep Research 官方特别强调，sub-agent 工具调用会产生大量原始网页、失败工具调用和无关网站结果；如果不做清洗，token usage 会显著膨胀。 之前的 harness engineering trace 中出现的 YouTube、Reddit、二手博客、论坛混入，本质上就是 tool-feedback expansion 和 source pruning 不足的表现。

第四，缺少 effort scaling（努力程度缩放）机制

    Anthropic 明确建议根据问题复杂度分配研究资源：简单事实查询只需要 1 个 agent 和少量工具调用，直接比较任务才需要 2–4 个 subagents，复杂研究才适合更多 subagents；这种规则用于防止简单问题被过度投入。 你当前项目的问题正是：具备深研究能力，但还没有稳定地区分“需要深研究”和“只需要 MVP 回答”的任务。


## 策略一 配置 提示词 和 模型调度


### 配置层

---**本质上是做了基于规则的并发控制**

一. 结构化输出最大重试次数max_structured_output_retries默认值3->1。
   
    这样做的原因是我认为我将调用的模型的结构化输出能力一定是稳定可靠的，绝大部分情况下结构化响应不会出错，极端情况下可以直接结束流程，无需为了极端情况而放宽重试次数加大token bloat风险。

二. 最大并发研究单元数量max_concurrent_research_units默认值5->3。

    这是指每轮supervisor能够同时调用的ConductResearch的个数，即研究者的个数，直观上是决定了研究的**广度**的唯二之一因素。我认为暂时的收紧这个值有利于控制成本，后续可以再放宽。实际上，我认为我进行评估时，大部分情况下是不需要大于三个子主题同时开展研究的。

三. Research Supervisor 最大研究迭代次数max_researcher_iterations默认值6->3

    这是指supervisor能够进行的最大迭代次数，直观上看其是决定研究**深度**的唯二之一因素。我认为我暂时希望评估的内容不会涉及太深太复杂的询问，所以暂时收紧以后可逐渐放宽。

四. 单个 researcher step 中最大工具调用次数max_react_tool_calls默认值10->5

    这是指单个researcher能够执行的工具调用节点的最大轮数，其是决定研究**深度**的唯二之一因素。我认为我暂时希望评估的内容不会涉及太深太复杂的询问，所以暂时收紧以后可逐渐放宽。

五. **配置**researcher每次轮工具调用最大并行工具调用个数max_concurrent_researcher_tool_calls 默认值None->3 同步追加到researcher的系统提示词

    这是指researcher每次轮工具调用最大并行工具调用个数，直观上其决定研究**广度**的唯二之一因素。我认为我进行评估时，每个子主题大部分情况下是不需要大于三个工具并发开展研究的。

六. **配置**限制一次 tavily_search 内部查询最大执行个数max_queries_per_search_call 默认值None->3 同步追加到researcher的系统提示词

    这是指tavily_search 内部查询最大执行个数，同时会复用该值限制网页摘要任务的并发度。直观上其是决定研究**深度和广度**的工具因素。

    tavily_search 工具内部也会并行执行多个 query，并且对每个 unique URL 并行调用摘要模型。所以即使 researcher 只发出 1 个 tavily_search tool call，内部也可能放大成多次 Tavily 请求和多次模型摘要请求。这会影响是否需要新增“每轮 researcher tool call 并发数”限制的判断。


七. 压缩并综合单个 researcher 的研究结果的compress_research节点的压缩尝试次数max_attempts默认值3->1

十. 小结：

    经过上述收紧后，系统从“默认深研究 + 高并发扩展”调整为“受控研究 + 成本优先”的执行模式。

    核心控制结果(暂时忽略thinktool的调用)如下：

| 指标                 |                原理论上限 |                   调整后理论上限 | 控制目标                                                                       |
| ------------------ | -------------------: | ------------------------: | -------------------------------------------------------------------------- |
| 最大 Tavily 内部 search query 请求数         | `6 × 5 × 10 × m × n` | `3 × 3 × 5 × 3 × 3 = 405` | 控制搜索、工具调用和网页摘要的 fan-out                                                    |
| 最大语言模型调用上限         |                未显式收敛 |                  `2088` 次 | 控制 supervisor、researcher、summarization、compression、final report 等节点的总体调用规模 |
| 启用澄清模式后的最大语言模型调用上限 |                未显式收敛 |                  `2089` 次 | 额外增加 1 次 clarification 判断                                                  |

    调整后的关键配置如下：

| 控制项                                    | 原默认值 | 调整后 | 控制目标                       |
| -------------------------------------- | ---: | --: | -------------------------- |
| `max_structured_output_retries`        |    3 |   1 | 降低异常重试成本                   |
| `max_concurrent_research_units`        |    5 |   3 | 限制 Supervisor 研究广度         |
| `max_researcher_iterations`            |    6 |   3 | 限制 Supervisor 研究深度         |
| `max_react_tool_calls`                 |   10 |   5 | 限制单个 Researcher 工具轮次       |
| `max_concurrent_researcher_tool_calls` | None |   3 | 限制 Researcher 单轮工具并发       |
| `max_queries_per_search_call`          | None |   3 | 限制 Tavily 内部 query 与网页摘要并发 |
| `compress_research.max_attempts`       |    3 |   1 | 降低压缩重试成本                   |

    当前配置下，理论最大语言模型调用数为：

    `1 + 4 + 45 + 2025 + 9 + 4 = 2088`

    其中：

| 部分                |      调用数 |
| ----------------- | -------: |
| Research Brief 生成 |        1 |
| Supervisor 调用     |        4 |
| Researcher 推理调用   |       45 |
| Tavily 网页摘要调用     |     2025 |
| Research 压缩调用     |        9 |
| Final Report 生成调用 |        4 |
| **合计**            | **2088** |

    如果启用澄清模式，则额外增加 1 次 clarification 判断，总上限为：

    `2088 + 1 = 2089`

    因此，当前策略的核心结论是：系统仍保留 DeepResearch 的多轮检索、多智能体和网页摘要能力，但通过限制 Supervisor 广度、Researcher 深度、工具并发、Tavily 内部 query 数和压缩重试次数，将最坏情况下的工具调用和模型调用规模显式收敛，避免简单评估任务被过度研究。




### 提示词层

一. 简报生成系统提示词中明确****

当前简报生成提示词天然容易造成 token bloat，主要存在以下问题：

    1. 同时要求“最大化具体性与细节完整度”并“包含所有细节”，容易将无关信息、重复要求和次要背景写入简报。
    2. 对用户未提供的必要属性，统一要求写成“开放项”或“无约束”，容易产生大量没有实际价值的补充说明。
    3. 没有明确规定“具体化”的边界，可能在整理用户需求时擅自增加研究对象、分析维度或交付要求，造成任务范围扩张。
    4. 来源规则没有根据任务类型和复杂度按需触发，而是倾向于将完整的来源要求加入所有任务。
    5. 来源策略覆盖不够全面，未明确不同来源的优先级、适用场景以及非权威来源的使用边界。

    针对以上问题，应进行以下调整：

    a. 根据任务复杂度控制简报的具体程度。不要为了追求完整而无必要地扩大任务范围；对于简单问题，只保留回答所需的关键信息；对于复杂研究任务，则应保留足够的背景、约束和关键维度，使研究者能够充分完成任务。

    b. 保守处理用户未说明但确实必要的维度。只有当某项信息会实质影响研究路径、结论可靠性或最终交付时，才将其简洁说明为开放项或不设特定限制，不要逐项列出与任务无关的“未指定”条件。

    c. 避免无依据的假设。用户未提供的信息不得自行编造，也不得擅自增加研究对象、比较维度、时间范围、地域范围或输出要求。

    d. 明确来源优先级和研究策略。对于简单问题，应直接定位需要核实的关键事实，优先从最相关的官方来源、一手来源或权威来源中获取直接证据，避免无必要的广泛搜索。对于复杂研究任务，应采用“由广到窄、由浅入深”的研究策略：先识别问题范围、核心实体和主要方向，再逐步聚焦关键问题，并使用权威来源深入核实核心结论。非权威来源可在发现线索、补充背景或了解实际体验时适量参考，但不能作为核心结论的主要依据，也不应因追求来源数量而过度搜索。



二、监督智能体系统提示词中明确任务委派、停止规则和并行管理

    a. 根据任务复杂度分配研究资源。默认优先使用单个研究智能体，只有当任务存在明确、独立且不重叠的研究方向时，才并行委派多个子智能体。

    b. 明确停止规则。当用户要求的关键维度已经覆盖、核心结论已有充分可靠的证据，且继续研究的预期信息增益较低时，应调用 `ResearchComplete`，避免为了追求完美而持续委派。

    c. 设置确定性的委派轮数和并发上限。提示词负责引导监督智能体节省预算，代码负责截断超出 `{max_concurrent_research_units}` 的并行子任务，形成“启发式规则 + 硬限制”的双层控制。

三、监督智能体系统提示词中明确子任务拆解与证据覆盖评估

    a. 每个子任务应具有清晰的研究目标、任务边界、关键问题、来源要求和预期输出，避免不同子智能体重复研究或遗漏关键维度。

    b. 对于横向比较任务，各子智能体应使用一致的评价维度和证据标准，以便最终结果能够直接比较和合并。

    c. 子智能体返回结果后，监督智能体不仅判断“是否还有信息缺失”，还应检查核心结论是否得到权威来源支持、是否存在来源冲突，以及追加研究能否产生实质性信息增益。

四、研究智能体系统提示词中明确搜索预算、停止规则和并行管理

    a. 根据任务复杂度设置搜索工作量启发式规则。该规则主要约束搜索轮数、工具调用数和查询规模，并不等同于直接控制 Token；实际 Token 和费用仍应由运行指标单独统计。

    b. 明确单轮并行工具调用数、单次搜索查询数和每个查询结果数，并由代码实施硬限制，防止模型违反提示词后造成搜索规模失控。

    c. 停止条件应以需求覆盖程度、证据质量和新增信息增益为核心，而不是机械地以来源数量作为完成标准。当最近的搜索没有产生新的关键事实、更高质量来源或新的有效方向时，应停止继续搜索。

    d. `think_tool` 应用于初始规划、结果冲突、明显信息缺口和结束前检查等关键节点，不必在每一次成功搜索后强制调用，以减少无效模型轮次和上下文开销。

五、根据任务复杂度选择搜索策略和来源层级

    对于简单、明确的事实查询，应直接定位需要核实的关键事实，优先使用最相关的官方来源、一手来源或权威来源，不进行无必要的广泛搜索。

    对于复杂、开放式研究任务，应采用“由广到窄、由浅入深”的策略：先建立整体问题地图，识别核心实体、主要方向和关键争议，再选择高价值方向深入研究，最终通过权威证据链收敛为结论。

    官方文档、原始论文、政府或标准机构资料、官方数据和项目官方仓库应作为核心证据。非权威来源可以用于发现线索、补充背景、了解实际体验或识别争议，但不能单独支撑关键事实，也不应为了增加来源数量而过度搜索。


五.为防止summery阶段产生过多上下文，调整其提示词保留比例默认值 25-30 -> 10-15


### 模型调度层

一. 基于规则的成本感知模型调度（Cost-aware Model Orchestration）：
   
    a.不同的调用根据所处任务的复杂度和重要性使用不同强度的模型 

    b.不同的任务需求使用具有不同的能力或画像的模型。

    c.Supervisor/final_report_model 用“强但受控”的模型，Researcher 用“主力但成本可控”的模型，Summary/Compression 用低成本模型，Critic 用高价值模型。

- research_model:高 使用计划推理和思考能力突出的模型 例如claude fable5、glm-5.2、**Qwen3.7-plus(较高质量且限时降价)**
- summarization_model:中低 使用长上下文和总结提炼能力突出的模型 例如 gemini3.1、
- compression_model:中 使用长上下文和总结提炼能力突出的模型 例如 gemini3.1 pro
- final_report_model:高 使用思考推理总结写作等综合能力全面的模型 例如 chatgpt5.5

配置如下：

- SUPERVISOR_MODEL=glm-5.2 max / qwen3.7-plus # 高价值**强**模型
- RESEARCHER_MODEL=qwen3.7-plus # 均衡模型
- SUMMARIZATION_MODEL=qwen3.5-flash # 低成本**快**响应模型
- COMPRESSION_MODEL=qwen3.5-flash # 低成本快响应模型
- FINAL_REPORT_MODEL=glm-5.2 max / qwen3.7-plus # 高价值强模型
- CRITIC_MODEL=glm-5.2 max/ qwen3.7-plus # 高价值强模型
