# DeepResearch 多智能体系统评测体系设计报告
## 概述

### 背景

DeepResearch 并不是一次普通的大模型问答，而是一类由任务理解、研究规划、子任务拆分、并行检索、工具调用、证据筛选、上下文压缩和报告生成共同组成的**长链路 Agent 系统**。对于多智能体架构而言，Supervisor 还需要根据用户目标**动态制定研究策略**，并将任务委派给多个 Researcher；各 Researcher 则在独立上下文中持续检索、判断信息质量并返回压缩后的研究结果。

这类系统具有**开放性、动态性和非确定性**。面对相同问题，不同运行可能调用不同工具、访问不同来源、采用不同任务拆分方式，但仍然得到同样合理的结论。因此，评测**不能简单要求系统执行预先规定的唯一轨迹**，而应同时判断**最终结果是否正确**，以及系统是否通过**合理、可靠且经济的过程得到这一结果**。Anthropic 在其多智能体研究系统实践中明确指出，研究过程具有动态和路径依赖特征，同一任务可能存在多条有效执行路径；OpenAI 与 LangSmith 也分别将 Agent 评测扩展到完整 Trace、最终响应、执行轨迹和单步决策。

### 建设原因

传统的大模型评测通常侧重**最终答案正确率、文本相似度或主观质量评分**，但这些指标不足以解释 DeepResearch 系统为何成功或失败。

一份报告可能语言流畅、结构完整，却存在以下问题：

* 引用**来源无法支持对应结论**；
* Supervisor **遗漏了用户的重要约束**；
* 多个 Researcher **重复**研究相同问题；
* 搜索 Query 与子任务**目标不匹配**；
* 工具调用参数**错误但未进行恢复**；
* 上下文压缩**丢失关键**数字、限定条件或来源；
* 系统已经获得**足够证据**，却仍持续搜索并产生**过度扇出**；
* 最终答案正确，但消耗了**远超任务价值的 Token、时间和工具调用**。

因此，仅评估最终报告，只能观察系统的外部结果，无法判断内部工作流是否可靠，也无法将问题准确定位到 Research Brief、Supervisor、Researcher、工具、压缩或最终写作模块。

成本指标同样不是附属指标。Anthropic 的研究系统数据显示，Token 用量、工具调用数量和模型选择能够解释其浏览评测中大部分性能差异；与此同时，其多智能体系统的 Token 用量显著高于普通聊天交互。这说明研究质量与计算投入之间存在明确联系，评测必须同时考察“完成得怎么样”和“以什么代价完成”。

### 基本原理

本项目采用以 Evaluation-driven Development（评测驱动开发）为核心的混合评测方法：

> 评测集驱动 + 确定性规则检查 + LLM-as-Judge + Agent 轨迹评测 + 人工校准 + 版本回归测试。

其基本过程是：

1. 使用固定**评测集**提供稳定、可重复的任务输入；
2. 将每个任务拆解为明确的**成功条件**、内容要求与形式约束；
3. 使用代码评测器检查字数、格式、来源数量、字段完整性和工具参数等确定性条件；
4. 使用 LLM-as-Judge 评价**正确性、完整性、论证合理性、来源质量和报告表达等开放性指标**；
5. 结合**完整 Trace 分析模型调用、工具调用、Agent 交接、异常、重试和节点流转**；
6. 对 Supervisor、Researcher 和工具调用中的**关键单步决策进行局部评测**；
7. 通过人工抽查和专家标注校准自动评分；
8. 在模型、提示词、工具或参数发生变化后运行同一评测集，比较质量、成本和延迟的变化。

这一方法与当前主流工程实践一致。OpenAI 将自定义评测流程概括为定义目标、收集数据集、定义指标、运行比较并持续评测，同时强调尽早建立评测、记录完整日志并通过人工反馈校准自动评分。 LangSmith 则将人工、代码、LLM-as-Judge 和 Pairwise Evaluation 作为互补方法，并支持同时使用运行输入、输出与中间执行步骤进行评分。

### 评测集设计依据

项目构建了包含 20 个样例的初始评测集，划分为**简单事实任务**、**约束明确的简短说明**、**开放式判断**、**多产品比较**和**技术方案设计**五类任务，每类设置四个样例，并覆盖**智能体、IT 技术和日常生活**等不同领域。

这一规模适合作为项目早期的开发集和回归集。Anthropic 在多智能体研究系统的早期开发中，同样从约 20 个能够代表真实使用方式的问题开始评测，并指出早期版本之间通常存在较大的效果差异，少量高质量样例即可发现明显回归。LangSmith 当前的评测实践也建议从 10–20 个覆盖常见情况与边界情况的人工策划样例开始，再逐步吸收生产 Trace、失败案例与合成数据。

因此，这 20 个样例可以合理定位为：

* 项目级初始评测集；
* 开发阶段的快速回归集；
* 模型、提示词和参数的横向比较集；
* 失败模式发现与评测标准校准集。

但它暂时不应被描述为能够代表所有 DeepResearch 场景的完整行业 Benchmark。后续还应增加隐藏测试集、对抗样例、边界样例、真实用户任务以及多次重复运行，以降低过拟合和偶然性影响。

### 核心评测框架

本体系采用“**结果—过程—效率—可靠性**”四层评价结构。

#### 1. 结果层

判断系统最终是否完成了用户真正提出的任务，主要包括：

* 任务完成率与内容**正确性**；
* 幻觉率和事实**真实性**；
* 引用与关键主张之间的**一致性**；
* 来源**权威性**和证据链**完整性**；
* 最终报告的完整性、连贯性和约束遵循。

结果层回答的是：

> 系统最终给出的答案是否正确、可信并真正解决了用户问题？

#### 2. 过程层

评价系统获取最终结果的**研究路径是否合理**，主要包括：

* Research Brief 是否完整保存用户目标和限制；
* Supervisor 是否进行了合理的规划、拆分、调度和终止判断；
* Researcher 是否生成了有效 Query 并选择了适合的工具；
* 工具调用顺序和参数是否正确；
* 反思是否识别了真实的信息缺口；
* 工具失败后是否重试、修正或降级；
* Agent 之间的信息交接是否完整；
* 上下文压缩是否保留了关键证据。

过程层回答的是：

> 系统为什么得到了这一结果，其执行行为是否合理？

复杂 Agent 的过程评价需要覆盖最终响应、完整轨迹和关键单步三个粒度，但不能简单要求所有运行复制同一条路径。合理做法是定义必须满足的过程约束，例如“关键数据必须经过权威来源核验”“调用工具时参数必须合法”“研究完成后应及时终止”，而不是规定系统必须按照固定工具序列执行。

#### 3. 效率层

评价系统付出**的资源是否与任务难度和信息增益相匹配**，包括：

* 输入与输出 Token；
* 模型调用和工具调用次数；
* 并行 Researcher 数量；
* 搜索 Query 和网页处理数量；
* 端到端延迟及分阶段耗时；
* 重复搜索和重复结论比例；
* 每轮新增有效信息；
* 每项有效结论消耗的 Token 与工具调用。

效率层不主张“Token 越少越好”，而是判断额外**投入是否带来了相应的正确性、覆盖度和证据质量提升**。复杂研究任务可能合理地需要更多 Token 和工具调用，但无效循环、重复研究和无新增信息的搜索应被视为成本浪费。

#### 4. 工程可靠性层

评价系统作为工程系统是否具备稳定运行和持续演进能力，包括：

* 工具与 MCP 返回是否正确、完整和可解析；
* 结构化输出是否稳定；
* 错误发生后能否恢复；
* Trace 是否足以复现和诊断问题；
* 工作流节点和状态传递是否正常；
* 尚未完成模块的设计是否具备合理需求、接口和验证方案。

OpenAI 将 Trace 定义为一次执行中模型调用、工具调用、Guardrail 和 Handoff 的端到端记录，并建议利用结构化 Grader 定位工作流级回归；Anthropic也强调完整生产 Trace 是区分搜索 Query、来源选择和工具故障等失败原因的必要条件。

### 评分设计关键

本体系使用 16 个评价条目，但需要将其理解为“15 个基础维度 + 1 个派生总体得分”。

总体得分不应由 Judge 再凭整体印象独立生成，而应由有效分项按照固定权重计算，以保证总分与分项结论一致。

同时，需要明确以下边界：

* 任务真实率：评价最终内容中事实正确的比例和幻觉程度；
* 真实性与证据链：评价来源质量以及引用是否真正支持结论；
* 工具调用正确率：评价 Agent 是否正确选择和调用工具；
* 工具或 MCP 反馈质量：评价工具系统本身返回的结果是否正确、完整和可用；
* 错误恢复率：仅在确实发生错误时评分，未发生错误应标记为“不适用”；
* 未来模块质量：属于设计审查指标，不应默认参与每次运行的总体得分。

另外，单个宽泛维度不应只依赖一句描述直接得到 0–10 分。更可靠的方式是将每个维度继续拆分为若干原子化、可观察的子标准，例如：

* 是否回答核心问题；
* 是否满足全部显式限制；
* 关键结论是否有引用；
* 引用是否直接支持结论；
* 是否优先使用一手来源；
* 是否出现重复无效搜索；
* 失败后是否调整参数；
* 终止决策是否合理。

先对这些原子子项进行通过/不通过或分级评分，再汇总为 10 分制维度得分。DeepResearch Bench II 的核心经验正是通过细粒度、可验证的 Rubric 提高评测的可解释性和与专家判断的一致性。

### LLM-as-Judge 的使用原则

LLM-as-Judge 适合评价开放式研究报告，因为此类输出通常没有唯一标准答案，难以通过字符串匹配完成自动评分。Anthropic 在实际研究系统中使用 Rubric 评价事实准确性、引用准确性、完整性、来源质量与工具效率，并通过 LLM Judge 实现规模化评测。

但 LLM Judge 不应成为唯一评测来源。本项目应采用以下组合：

| 评价对象                | 推荐方法                 |
| ------------------- | -------------------- |
| 字数、格式、字段、链接数量       | 代码或规则检查              |
| 工具名称、参数 Schema、调用次数 | Trace + 代码评测         |
| 简单事实答案              | 参考答案 + 权威来源核验        |
| 报告完整性、连贯性、方案合理性     | LLM-as-Judge         |
| 两个系统版本的相对优劣         | Pairwise Judge 或人工对比 |
| 引用是否支持主张            | Claim–Evidence 对齐评测  |
| 关键或争议样例             | 人工复核                 |
| Judge 自身准确性         | 人工标注集校准              |

OpenAI 强调 LLM 更擅长进行分类、比较或依据明确标准评分，而不是进行缺少约束的开放式判断；LangSmith也指出 LLM-as-Judge 需要持续审查、提示词调优和 Few-shot 校准。

### 作用

该评测体系具有五项直接作用。

第一，建立稳定的质量基线。通过固定任务集、固定评分标准和固定模型配置，可以比较不同版本的实际表现。

第二，定位失败根因。最终报告得分下降后，可以继续检查问题来自任务理解、Supervisor 规划、Researcher 检索、工具反馈、上下文压缩还是报告生成。

第三，支持模型与参数选择。通过比较质量、Token、工具调用和延迟，可以判断更强模型、更高并发或更长研究是否带来了足够收益。

第四，发现工作流回归。提示词、工具描述、模型版本和路由逻辑的微小变化都可能改变多智能体行为，固定评测集和 Trace Grading 能够及时发现这些变化。

第五，形成持续迭代闭环。OpenAI 将成熟评测流程描述为持续执行的改进循环：明确目标、积累数据、定义指标、运行比较，并不断从真实日志和失败案例中扩充评测集。

### 意义

该体系的意义不只是为 DeepResearch 系统生成一个分数，而是把原本依赖主观体验的 Agent 开发，转变为**可观察、可解释、可复现和可回归的工程过程**。

它能够同时回答四个问题：

1. 系统是否完成了正确的任务？
2. 报告中的事实和证据是否可信？
3. Supervisor、Researcher 和工具链是否采用了合理过程？
4. 获得这一结果所付出的 Token、时间和调用成本是否值得？

在此基础上，项目可以形成：

> 采集 Trace → 发现失败模式 → 构建评测样例 → 量化比较版本 → 定向修改模型、提示词或工作流 → 回归验证

这一闭环使 DeepResearch 系统的优化不再依赖少量演示案例或“看起来更好”的主观判断，而是建立在任务级指标、过程级证据和成本数据之上。

### 一句话总结

本评测体系通过“**代表性评测集、混合自动评测、全链路 Trace 分析和人工校准**”，系统衡量 DeepResearch 是否**正确完成任务、是否依据可信证据、是否采用合理研究过程，以及是否以可接受的成本稳定完成执行**。



## 1. 评测目标

本项目面向 DeepResearch 多智能体系统构建了一套覆盖“最终结果质量、智能体执行过程与系统运行效率”的综合评测体系。评测不仅关注最终报告是否正确，还进一步分析系统是否正确理解任务、合理规划研究路径、有效调用工具、处理执行异常、构建可信证据链，并在可接受的 Token 成本和响应延迟内完成任务。

与仅根据最终答案进行打分的传统评测方式相比，本体系将 DeepResearch 视为一个由 Research Brief、Supervisor、Researcher、搜索工具、MCP 服务、上下文压缩和报告生成模块共同组成的完整执行系统，通过联合分析最终报告和中间执行轨迹，定位系统性能变化背后的具体原因。

评测体系主要用于：

1. 衡量不同**模型、提示词、工具配置和工作流版本的整体性能**；
2. 识别**幻觉、证据不足、任务遗漏和约束违反等结果问题**；
3. 诊断任务**拆分不合理、搜索查询失效、研究过度扇出和错误恢复不足等过程问题；**
4. **比较系统版本之间的效果、成本与延迟变化**；
5. 为**模型调度、上下文治理、并发控制和智能体终止策略提供优化依据**。

## 2. 评测集设计

项目自主设计了包含 20 个样例的 DeepResearch 评测集，共划分为 5 类任务，每类任务设置 4 个差异化样例。

| 任务类型      | 主要考查能力           | 典型评测重点                            |
| --------- | ---------------- | --------------------------------- |
| 简单事实任务    | **精确检索和事实确认**        | 是否直接回答、事实是否正确、是否优先引用一手来源          |
| 约束明确的简短说明 | **指令理解和约束遵循**        | 字数、格式、来源数量、内容范围等限制是否全部满足          |
| 开放式判断     | **信息收集、比较分析和不确定性处理** | 是否充分搜索候选对象、判断标准是否合理、是否避免无依据的绝对结论  |
| 多产品比较     | **多实体、多维度的信息对齐**     | 产品范围是否完整、数据口径是否一致、时间截点和来源是否可靠     |
| 技术方案设计    | **需求分析、架构设计和工程权衡**   | 方案是否完整可落地、组件选择是否合理、是否分析成本、风险和替代方案 |

样例覆盖智能体、IT 技术和日常生活等不同应用场景，并通过改变提示词表达形式构造不同难度：部分任务包含来源、格式、字数、时间范围和输出结构等多项明确限制；部分任务仅提供开放问题，不额外限定研究范围。

这种设计同时考查系统在以下两类环境中的能力：

* **强约束环境**：系统能否准确解析并执行显式要求；
* **弱约束环境**：系统能否自主确定研究边界、判断标准和报告结构。

20 个样例更适合作为项目级回归评测集，用于比较系统内部版本和配置变化，而不宜直接宣称能够代表所有 DeepResearch 任务。为降低系统针对固定样例过拟合的风险，评测集应保持版本锁定，并逐步增加隐藏样例、边界样例和失败案例。

## 3. 方法依据

DeepResearch 系统的输出通常具有开放性、长文本、多来源和多步骤执行等特点，仅依靠字符串匹配或单一参考答案难以准确判断报告质量。因此，本项目采用 LLM-as-Judge 作为主要自动化评分方法，并结合规则检查、来源验证和执行轨迹分析。

相关研究表明，强模型作为评审者能够在开放式任务中较好地近似人类偏好，但同时可能存在位置偏差、长度偏好和自我偏好等问题，因此不能将 Judge 模型的单次评分直接视为绝对真值。

DeepResearch Bench 将深度研究系统的评测拆分为报告质量、信息检索能力、有效引用数量和引用准确性等部分，说明评测 DeepResearch 系统不能只检查最终文本，还必须评价信息收集与证据引用能力。

DeepResearch Bench II 进一步指出，**过于宽泛或完全由 LLM 临时生成的评价标准可能导致评分难以验证**，并采用**细粒度、原子化和可核验的 Rubric 提升评测结果与专家判断的一致性**。

因此，本项目采用以下设计原则：

* 明确化：每个评分维度均给出具体评价对象，不使用“整体感觉良好”等模糊标准；
* 证据化：所有评分必须结合最终报告、执行日志、工具返回或引用来源给出理由；
* 分层化：分别评估任务结果、智能体能力、工具链路和运行效率；
* 可比较：所有有效指标统一采用 0–10 分制，便于跨任务和跨版本比较；
* 可诊断：评分结果必须能够映射到具体工作流节点或系统模块；
* 缺失不猜测：无法获得必要证据时标记为“暂无法评分”，不根据最终结果反推内部执行过程。

## 4. 多维评分框架

评测体系包含 15 个基础评价维度和 1 个派生总体得分，共计 16 项。

| 维度           | 评价内容                                               |
| ------------ | -------------------------------------------------- |
| 总体得分         | 对其余有效维度进行加权汇总，反映系统本次任务的综合表现                        |
| 任务完成率        | 核心问题是否回答正确，显式与隐式要求是否完成，是否存在内容遗漏或范围偏离               |
| 任务真实率        | 报告中是否存在编造事实、错误数据、虚假引用或无证据推断；分数越高代表幻觉越少             |
| 工具调用正确率      | 工具选择和调用顺序是否合理，参数是否符合 Schema，搜索范围和调用时机是否正确          |
| 错误恢复率        | 调用失败、结构化输出失败、超时或 Token 超限后，系统是否正确重试、调整参数或采用降级策略    |
| 真实性与证据链质量    | 来源是否权威，结论与引用是否一一对应，是否能够从原始来源验证报告中的关键主张             |
| 反思质量         | Supervisor 和 Researcher 的反思是否识别真实的信息缺口，并转化为有效的后续行动 |
| 简报书写质量       | 是否正确理解用户意图，是否需要澄清，Research Brief 是否完整保留任务边界和约束     |
| 监督智能体质量      | 是否制定合理研究计划，正确拆分子任务，控制子主题边界，并根据阶段性结果进行补充调度和终止判断     |
| 研究智能体质量      | 是否构造有效搜索 Query，选择正确工具，充分利用检索结果，并开展必要的交叉验证和补充检索     |
| 最终报告质量       | 报告是否完整、连贯、结构合理，内容是否准确，是否满足格式、篇幅、引用和表达要求            |
| 成本           | Token、模型调用、工具调用和搜索次数是否与任务难度匹配，是否出现重复研究或过度扇出        |
| 延迟           | 端到端耗时及各阶段耗时是否合理，并发机制是否真正降低等待时间                     |
| 整体执行流程       | 节点跳转、智能体循环、上下文传递、压缩和终止流程是否顺畅合理                     |
| 工具或 MCP 反馈质量 | 工具返回内容是否正确、完整并可解析，是否存在截断、格式污染、错误映射或无效反馈            |
| 未来模块质量       | 对尚在设计或开发中的模块，评价其需求合理性、架构完整性、接口设计、可实现性和测试方案         |

其中，“总体得分”不是独立观察指标，而是对其余有效维度的综合计算结果。这样可以避免 Judge 在已经完成分项评分后，再凭整体印象给出一个与分项结果不一致的总分。

## 5. 评分标准

所有维度统一采用 0–10 分制：

| 分数范围   | 评价等级 | 基本含义                         |
| ------ | ---- | ---------------------------- |
| 9–10 分 | 优秀   | 几乎完整达到目标，仅存在不影响结果的轻微问题       |
| 7–8 分  | 良好   | 主要目标完成，存在局部遗漏或可明确改进的问题       |
| 5–6 分  | 基本合格 | 核心任务部分完成，但正确性、完整性或执行过程存在明显缺陷 |
| 3–4 分  | 较差   | 仅完成少量要求，存在较严重错误、遗漏或流程失效      |
| 1–2 分  | 严重失败 | 输出与任务要求大幅偏离，关键事实或执行流程基本不可用   |
| 0 分    | 完全失败 | 未生成有效结果，或结果完全错误且不存在可用内容      |

对于错误恢复率等依赖特定事件的指标，如果本次执行未发生任何错误，不能简单判定为 10 分。此时应标记为“不适用”或“证据不足”，避免把“没有触发恢复机制”误认为“恢复机制表现完美”。

同理，未来模块质量只在提供模块需求、方案、代码、接口或实验结果时进行评分，否则不纳入总体得分。

## 6. 推荐权重与总体得分

为避免所有指标被简单等权处理，本项目可按照结果质量、执行过程、智能体能力和运行效率设置推荐权重：

| 评价类别  | 包含维度                          |  权重 |
| ----- | ----------------------------- | --: |
| 结果质量  | 任务完成率、任务真实率、真实性与证据链、最终报告质量    | 44% |
| 执行过程  | 工具调用、错误恢复、整体流程、工具或 MCP 反馈     | 20% |
| 智能体能力 | 简报、Supervisor、Researcher、反思质量 | 26% |
| 运行效率  | Token 成本、执行延迟                 |  8% |
| 演进能力  | 未来模块质量                        |  2% |

总体得分计算方式为：

总体得分 = Σ（分项得分 × 分项权重）÷ 100

当某个指标为“不适用”或“暂无法评分”时，从本次计算中移除该指标，并按剩余有效权重重新归一化。这样能够防止缺失数据被错误地计为零分，也可以避免不同执行记录之间因可观测信息量不同而产生不公平比较。

对于不同类型任务，还可以在保留统一总分的基础上突出不同重点。例如，简单事实任务更重视正确性、来源质量和检索效率；开放式判断更重视研究覆盖、判断依据和不确定性表达；技术方案设计则更重视需求理解、架构合理性和工程可落地性。

## 7. 评测执行流程

完整评测按照以下流程进行：

### 7.1 任务与约束解析

首先解析原始任务中的研究目标、实体范围、时间范围、来源要求、格式限制、字数限制和禁止扩展内容，形成可检查的任务约束清单。

对于约束型任务，可先通过规则程序检查字数、表格结构、来源数量、链接数量和指定字段，再由 LLM Judge 评价语义正确性与内容质量。确定性约束不应完全交由 Judge 模型判断。

### 7.2 执行轨迹还原

按照时间顺序整理：

用户输入 → 用户澄清 → Research Brief → Supervisor 规划 → 子任务拆分 → Researcher 查询 → 工具调用 → 工具反馈 → 研究反思 → 结果压缩 → 报告生成。

轨迹评测重点识别：

* 是否在没有必要时反复澄清；
* Supervisor 是否一次拆分过多子任务；
* 多个 Researcher 是否研究重复内容；
* Query 是否过宽、过窄或与任务无关；
* 工具调用失败后是否正确修正；
* 研究结果是否在压缩过程中丢失关键事实和引用；
* 系统是否在信息已经充足后继续无效搜索；
* 最终报告是否使用了执行过程中实际获得的证据。

### 7.3 声明—证据对齐

将最终报告中的关键结论拆解为可验证的 Claim，并逐条检查：

1. 该结论是否提供引用；
2. 引用是否指向真实存在的来源；
3. 来源内容是否支持该结论；
4. 数据、时间、对象和适用范围是否一致；
5. 是否将推测或二手观点错误表述为确定事实。

该步骤用于区分“引用数量较多”和“证据链真实有效”。报告附带大量链接，并不代表真实性得分一定较高。

### 7.4 分维度评分

Judge 必须针对每个维度分别输出：

* 评分；
* 评分依据；
* 发现的具体问题；
* 对应的执行证据；
* 可操作的改进建议。

禁止只输出分数而不解释，也应避免多个维度重复使用完全相同的评价内容。

### 7.5 成本与延迟分析

成本评价不能只根据总 Token 判断，还需要结合任务难度和有效产出，分析：

* 每个有效结论消耗的 Token；
* 每个有效结论对应的工具调用数量；
* 每轮研究带来的新增有效信息；
* 不同 Researcher 之间的内容重复率；
* 搜索结果进入上下文后的有效利用率；
* 压缩前后 Token 比例和信息保留情况。

延迟分析应区分模型生成时间、搜索工具时间、网页摘要时间、MCP 调用时间、压缩时间和最终报告生成时间，以判断真正的性能瓶颈。

## 8. 所需评测数据

为支持完整的 16 维评价，每次评测至少需要提供：

| 数据                   | 主要用途               |
| -------------------- | ------------------ |
| 原始任务输入               | 判断任务理解、正确性和约束完成情况  |
| 澄清记录与 Research Brief | 评价简报和任务范围提取能力      |
| Supervisor 完整轨迹      | 评价规划、拆分、调度、反思和终止决策 |
| Researcher 完整轨迹      | 评价搜索策略、工具选择和迭代研究过程 |
| 工具与 MCP 调用记录         | 检查调用顺序、参数、返回内容和异常  |
| 错误及重试日志              | 判断错误恢复和降级机制        |
| 压缩前后的研究内容            | 判断上下文治理和关键信息保留情况   |
| 最终报告                 | 评价正确性、真实性、完整性和表达质量 |
| Token、调用次数和费用        | 评价成本和过度扇出          |
| 各阶段时间戳               | 评价延迟和并发效果          |
| 参考答案或权威来源            | 为事实正确性提供外部基准       |
| 未来模块资料               | 评价尚未完成模块的设计与实现质量   |

如果只提供最终报告，可以评估任务完成率、真实性、证据链和报告质量，但无法可靠评价工具调用、错误恢复、Supervisor、Researcher 和整体执行流程。

## 9. LLM-as-Judge 的可靠性控制

为降低 Judge 模型自身偏差，评测过程采用以下控制策略：

1. 固定评分提示词、评分维度、模型版本和推理参数，保证不同实验之间的可比性；
2. 强制 Judge 先引用执行证据，再给出评分，减少纯主观判断；
3. 将可程序化验证的指标交给规则程序，不完全依赖 LLM；
4. 对关键样例进行人工复核，定期校准 Judge 与人工判断的一致性；
5. 避免使用与被测系统完全相同的模型作为唯一 Judge，降低自我偏好；
6. 对高争议任务进行多次评分或使用多个 Judge 聚合结果；
7. 对不同长度、顺序和表达方式的报告进行稳健性测试，检查长度偏好和位置偏差；
8. 保存 Judge Prompt、模型版本、原始评分和解释，确保评测过程可复现。

对于开放式判断和技术方案设计任务，Judge 应重点评价论证过程、证据覆盖和方案合理性，而不能仅因为结论与 Judge 自身偏好不同就扣分。

## 10. 结果分析方式

最终评测结果不只输出单次总体分数，还应形成以下分析视图：

* 任务类型得分：比较五类任务的能力差异；
* 维度得分：发现系统在正确性、检索、规划或成本方面的短板；
* Agent 得分：分别比较 Brief、Supervisor、Researcher 和 Final Writer；
* 失败类型分布：统计幻觉、引用错误、约束遗漏、无效搜索、过度扇出和终止失败；
* 成本—质量关系：判断额外 Token 和工具调用是否真正提升报告质量；
* 版本对比：比较不同模型、提示词和参数配置下的得分变化；
* 样例稳定性：观察同一任务多次运行的结果波动。

由于 Agent 系统具有随机性，重要版本应对关键任务进行重复运行。除平均得分外，还应记录最低得分和分数方差，以避免系统偶然生成一次高质量结果后掩盖稳定性问题。

## 11. 评测体系价值

该评测体系将 DeepResearch 的性能评价从“最终答案是否看起来不错”，扩展为对完整研究链路的可量化分析。

通过该体系，可以明确区分以下问题：

* 模型本身能力不足；
* Research Brief 丢失用户约束；
* Supervisor 任务拆分不合理；
* Researcher 搜索 Query 质量较低；
* 搜索或 MCP 工具返回内容有误；
* 压缩阶段丢失关键证据；
* Final Writer 未忠实使用研究结果；
* 并发和迭代配置造成 Token 浪费；
* 终止策略不合理导致研究过度扇出。

因此，该评测体系不仅用于给系统打分，更承担 Evaluation-driven Development（评测驱动开发）中的诊断作用：通过评测数据识别系统瓶颈，再针对模型、提示词、工具、状态管理和工作流参数进行定向优化，并使用固定评测集验证优化是否真正有效。

最终形成“评测—诊断—优化—回归验证”的闭环，使 DeepResearch 系统的迭代从主观体验驱动转变为基于证据和指标的工程化改进。
